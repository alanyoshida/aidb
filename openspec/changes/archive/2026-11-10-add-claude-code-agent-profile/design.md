# Design

## Context

Hoje só existe um perfil (`opencode`) e um harness (`OpencodeHarness`). A change `generalize-agent-runtime-plumbing` já tornou o provisionamento, o supervisor e a fila de execução agnósticos de agente: imagem, mount path de config, protocolo de harness e config_format vêm todos do perfil, nunca de um literal. O supervisor (`base-image/afsupervisor/supervisor.py`) sobe `profile["command"]` como um processo de vida longa (análogo a `opencode serve`), confinado por Landlock/seccomp conforme `profile["readable_paths"]`/`writable_paths`/`connect_tcp_ports` — ele nunca sabe que agente está rodando. O portal fala com esse processo via `HarnessPort` (`appaiforge/harness/base.py`), resolvido por protocolo em `AgentQueue.harness_for` (`agent_queue.py`).

A CLI `claude` em modo headless (`claude -p "<prompt>" --output-format stream-json`) não é um servidor: é um processo que roda até o fim do turno e sai, emitindo um evento JSON por linha no stdout. Isso não cabe direto no modelo "um processo de vida longa que o supervisor sobe e o harness fala HTTP com ele" que todo o resto da plataforma assume (`bind_tcp_ports`, Landlock de rede, `harness_port` no perfil).

## Goals / Non-Goals

**Goals:**
- Registrar `claude-code` como segundo perfil, provando que `agent-runtime`/`agent-sandbox` já são agnósticos de agente sem precisar editar nenhum dos dois.
- Implementar `ClaudeCodeHarness` falando o mesmo tipo de protocolo (HTTP contra um processo do container) que `OpencodeHarness`, para que `AgentQueue.harness_for` continue dispatando por protocolo sem mudança.
- Entregar paridade de UX do chat: streaming de mensagens, interrupção, continuidade de sessão, provedor/modelo por sistema.
- Critério de sucesso negativo do roadmap: zero edição em `afsupervisor/sandbox.py`, no proxy do gate de destrutivas (`base-image/dbproxy/`), ou nas regras de rede/Landlock existentes.

**Non-Goals:**
- Suportar o hook `PreToolUse` do Claude Code como um gate de aprovação equivalente ao `permission.asked` do opencode. O gate de SQL destrutivo já opera no data plane (proxy de conexão ao banco), comprovadamente agnóstico do protocolo de permissão do agente (spec `destructive-gate`, requirement "Gate do agente sobre SQL destrutivo"). Replicar esse hook seria segurança redundante e tocaria código novo de confinamento sem necessidade.
- Suportar a ferramenta nativa `question` (pergunta do próprio agente, distinta do gate) — sem equivalente simples na CLI headless; fica para uma change futura se for pedido.
- Seletor de perfil na UI de criação de sistema.
- Kubernetes (etapa 8).

## Decisions

### D1 — Shim HTTP no container, não exec remoto do portal
O container do agente roda um processo shim HTTP de vida longa (o que o perfil declara em `command`), do mesmo jeito que hoje roda `opencode serve`. O shim recebe `POST /session` (cria um id de sessão lógico, só local ao shim — não existe "criar sessão" na CLI antes do primeiro prompt), `POST /session/{id}/prompt` (invoca `claude -p "<prompt>" --output-format stream-json [--resume <claude_session_id>]` como subprocesso, lê stdout linha a linha, re-emite via SSE em `GET /event` no mesmo formato de envelope que o harness já consome) e `POST /session/{id}/abort` (mata o subprocesso em andamento).

Alternativa rejeitada: o portal fazer `docker exec` direto no container por prompt. Eliminaria o shim, mas introduziria um segundo mecanismo de harness (exec em vez de HTTP) só para este perfil, forçando o dispatch de `AgentQueue`/a declaração do perfil a conhecer "modo de transporte" além de protocolo — generalização que ninguém mais precisa hoje. HTTP uniforme mantém `harness_port`/`bind_tcp_ports`/Landlock de rede do perfil exatamente como já funcionam.

### D2 — Continuidade de sessão: mapear id lógico → id da CLI
A CLI gera seu próprio identificador de sessão no primeiro turno (aparece no evento `system`/`init` do stream-json) e espera `--resume <id>` nos turnos seguintes para manter contexto. O shim mantém, em memória, o mapeamento `id lógico do portal → id da sessão da CLI`, populado na primeira resposta e usado em todo prompt seguinte com `--resume`. Isso preserva o contrato existente do `HarnessPort.create_session`/`run` (o portal só conhece o id lógico) e a garantia generalizada em `agent-harness` ("mesmo identificador de sessão do harness em uso").

Risco aceito: se o processo shim reiniciar (crash, recriação do container), o mapeamento em memória se perde — mesmo efeito que hoje quando o container do opencode é recriado (`ChatSession.context_reset=True` já cobre esse caminho, requirement "Aviso explícito de reinício de contexto"). Nenhum comportamento novo a especificar.

### D3 — Config entregue via `~/.claude/settings.json`, credencial via env
`config_format: "claude-code-settings"` ganha um writer novo (`write_claude_code_config`, registrado em `_config_writers()` ao lado de `write_opencode_config` — mesmo padrão, zero mudança no dispatch) que grava `{"env": {"ANTHROPIC_BASE_URL": <base do broker, dialeto anthropic>}}` em `config_path`. A CLI já suporta um bloco `env` em `settings.json` e uma flag `--settings <path>` apontando para um arquivo fora do diretório padrão — paralelo exato de `opencode.json`'s `provider.anthropic.options.baseURL`. **Confirmado por spike real (tasks.md, task 1.3): dois requests reais bateram no stub local só com `--settings` apontando pra um arquivo fora do `$HOME` padrão, sem nenhuma env var `ANTHROPIC_BASE_URL` setada.**

`credential_env: "ANTHROPIC_API_KEY"` (literal, não `FROM_PROVIDER`) — **corrigido pelo spike real**: a hipótese original deste design era `ANTHROPIC_AUTH_TOKEN` (header `Authorization: Bearer`), mas o spike mostrou que (a) a CLI aceita `ANTHROPIC_API_KEY` (header `x-api-key`) e `ANTHROPIC_AUTH_TOKEN` igualmente, nenhum dos dois valida o formato da chave antes de mandar (um token no formato do broker, `<system_id>.<hmac>`, passou direto nos dois), e (b) o perfil `opencode` já usa `ANTHROPIC_API_KEY`/`x-api-key` pro dialeto anthropic (`services/catalog.py` PRESETS) — ou seja, o broker real já sabe trocar esse token quando chega por esse header. Usar `ANTHROPIC_AUTH_TOKEN` introduziria uma segunda convenção de header sem necessidade, arriscando um caminho que o broker pode não reconhecer. `ANTHROPIC_API_KEY` já é suportado por `resolve_credential_env` desde a change anterior (literal, não `FROM_PROVIDER` — teste `test_resolve_credential_env_literal_nao_delega`) e já injetado na env do container por `_broker_credential_env` sem mudança nenhuma em `provisioning.py` além do dispatch de config.
`--model <system.model>` é passado em todo `claude -p` pelo shim, lido do mesmo payload que hoje carrega `provider`/`model` para o opencode — preserva o requirement "Provedor e modelo declarados em cada execução" (harness nunca usa default próprio).

### D4 — Telemetria/auto-update da CLI desligados, não liberados no proxy
A CLI tenta, por padrão, checar atualização e mandar telemetria para hosts fora da allowlist do proxy HTTPS de saída (`default_https_allowlist`). Em vez de pedir a entrada desses hosts na allowlist (mudança em código de rede/segurança, o que o critério de sucesso proíbe), o shim invoca a CLI com as envs que ela já expõe para desligar essas chamadas (`DISABLE_TELEMETRY`, `DISABLE_ERROR_REPORTING`, `DISABLE_AUTOUPDATER`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`). Nenhuma mudança na allowlist nem no proxy.

### D5 — Imagem própria, menor superfície
`claude-code` tem sua própria imagem (`appaiforge/claude-code:0.1.0` ou similar), com só a CLI `claude`, o shim e o runtime necessário — não estende nem reusa a imagem `opencode`. Consistente com o roadmap ("uma imagem por agente, não uma com todos"). Exceção deliberada: `gated-mcp` (ver D6) é copiado pra esta imagem também — não é específico do opencode, é o único jeito que qualquer agente desta plataforma tem de ler o banco do sistema.

### D6 — Acesso ao banco via o mesmo `gated-mcp`, por `--mcp-config`
**Achado durante a implementação (não previsto no proposal original):** sem isto, o agente claude-code não teria NENHUM jeito de ler o banco de dados do sistema — `write_opencode_config` já prova que o acesso ao banco do opencode não é via bash solto, é exclusivamente via o MCP server `gated-mcp` (`/opt/gated-mcp/mcp_server.py`, uma ferramenta MCP por conexão, leitura classificada por `sqlgate.py`). Esse server é agnóstico de agente (um processo MCP stdio comum); só precisava de um jeito do claude-code carregá-lo.

Confirmado por spike real (sem depender do broker/chave real): a CLI aceita `--mcp-config <arquivo>` com o shape padrão `{"mcpServers": {"<nome>": {"command": [...], "args": [...]}}}` e `--strict-mcp-config` (ignora qualquer outra fonte de MCP, mesma postura de "perfil entregue sem segredo e sem surpresa" das outras partes do design). Um round-trip real (stdio de verdade, servidor FastMCP de teste) confirmou: o evento `system`/init reporta `"mcp_servers":[{"name":"...","status":"connected"}]`, a ferramenta aparece pro modelo como `mcp__<nome-do-server>__<nome-da-tool>`, e o `tool_result` que volta é o retorno real da ferramenta MCP — nada fake, nada por bash.

Implementação: `write_claude_code_config` (mesmo writer de D3) grava, no MESMO diretório de config montado só-leitura, um segundo arquivo `mcp-servers.json` com uma entrada por `DbConnection` do sistema (mesmo loop que `write_opencode_config` já faz, reaproveitando `_loopback_dsn`/`get_connection_secret`/o mesmo `/opt/gated-mcp/mcp_server.py`). O shim passa `--mcp-config <path> --strict-mcp-config` em todo `claude -p`. A imagem nova (D5) copia `gated-mcp` igual à imagem opencode.

**Atualização pós-implementação — corrigido em separado, nesta mesma sessão:** o pin `"mcp>=1.0"` no `base-image/Dockerfile` não tinha teto e já havia resolvido pra `mcp` 2.3.0 na imagem `appaiforge/base:0.1.0` publicada — ou seja, não era um risco hipotético: `from mcp.server.fastmcp import FastMCP` já estava quebrado em produção para qualquer sistema `opencode` com conexão de banco cadastrada (o `gated-mcp` é o único caminho de leitura do banco, D6 acima). Corrigido pinando exatamente (`mcp==1.30.0`, mesma versão e critério usados em `Dockerfile.claude-code`) em vez de só um teto solto, junto com as demais deps da mesma linha (`sqlglot`/`asyncpg`/`aiomysql`/`mysqlclient`/`google-cloud-bigquery`/`sqlalchemy-bigquery`) e as instaladas nas linhas vizinhas (`uv`, `pyseccomp`, `httpx`) — pinadas nas versões já validadas e rodando na imagem publicada (confirmado via `pip show` na imagem antes do rebuild), não em versões novas e não testadas. `appaiforge/base:0.1.0` e `appaiforge/claude-code:0.1.0` foram reconstruídos e o import do `FastMCP` confirmado funcionando nas duas.

## Achado crítico da verificação real (task 7.3) — bug pré-existente no `httpproxy`, corrigido em separado

**Confirmado com certeza, isolado até o nível de `base-image/httpproxy/proxy.py` puro, sem Docker, sem shim, sem CLI do claude envolvidos na causa:** o caminho de relay HTTP absoluto (`http://host/path`, usado por qualquer HTTP_PROXY/HTTPS_PROXY pra destino `http://`, diferente do túnel `CONNECT` usado por destino `https://`) **descartava inteiramente o corpo e todos os headers da requisição do cliente, exceto `Host`**. Reproduzido isoladamente: `_consume_headers` lia e jogava fora as linhas de header originais; o código só escrevia `Host`/`Connection: close` sintéticos pro upstream e nunca lia `client_reader` de novo pra repassar o corpo (só existia `_pump(up_reader, client_writer)`, nunca o sentido contrário, pro caminho não-CONNECT). Verificado ponta a ponta contra um stub real: toda requisição que chegava no destino tinha `headers: {"host":...,"connection":"close"}` e `body: {}`, sempre.

**Por que isso era grave pra claude-code (não só um detalhe do teste):** o perfil usa `ANTHROPIC_API_KEY`/`x-api-key` e o corpo (`messages`, histórico da conversa) em TODA requisição — ambos descartados por este bug. Contra um backend real e estrito (Anthropic/broker), isso falharia em TODO turno, não só no primeiro: sem `x-api-key` chegando, seria `401` sempre; mesmo com uma allowlist/proxy que não exigisse auth, sem `messages` chegando a conversa nunca teria contexto algum. Contra o stub fabricado deste teste (tolerante a corpo vazio), o efeito observado foi um loop infinito: o stub, sem nunca ver o `tool_result` do turno anterior, sempre respondia como se fosse o primeiro turno — o `claude -p` nunca via `stop_reason: end_turn` e ficava pedindo a mesma ferramenta pra sempre (confirmado: 750+ turnos em segundos, sem nenhum erro HTTP, zero chamada fora da allow-list).

**Por que isso NÃO era culpa do perfil/shim/harness desta change:** reproduzido com `claude` rodando direto no host (fora de qualquer container), contra uma cópia isolada de `proxy.py` (sem Docker, sem Landlock, sem supervisor) e um stub idêntico ao usado no resto do spike. O mesmo stub, sem proxy no meio (spike original, tasks 1.1-1.4), funcionou perfeitamente — a variável isolada era exclusivamente o proxy.

**Correção aplicada (fora desta change, em sessão separada, a pedido explícito do usuário):** `handle_client` agora captura os headers originais do cliente (`_read_headers`) em vez de descartá-los, repassa todos pro upstream no caminho HTTP absoluto (menos os hop-by-hop que o próprio proxy controla — `Host`/`Connection`/`Proxy-Connection`/`Proxy-Authorization`) e repassa o corpo da requisição pelo tamanho que os headers declaram (`_forward_request_body`: `Content-Length` ou `Transfer-Encoding: chunked`). Testes de regressão novos em `base-image/httpproxy/test_proxy.py` (headers/corpo chegam intactos no destino; hop-by-hop não é repassado). Com a correção e as imagens reconstruídas, `portal/tests/integration/test_claude_code_e2e.py` deixou de precisar do `skip` e passa de ponta a ponta de verdade (Docker real, shim real, CLI real, checkpoint real).

**Por que o perfil opencode aparentemente não era afetado:** não investigado a fundo (continua fora do escopo desta change), mas as evidências já coletadas (log do sidecar de um sistema opencode real, calmo, sem flood) sugerem que o cliente HTTP do opencode trata requisição proxy-para-`http://` de outro jeito (talvez sempre via `CONNECT`, tratando o proxy como opaco) — diferente do cliente do `claude` CLI (Bun fetch), que usa a forma absoluta padrão do HTTP pra destino `http://`, exercitando um caminho do proxy que não tinha cobertura de teste real antes deste achado. Isso deixou de ser um risco pra qualquer um dos dois agora que o bug em si está corrigido, independentemente de qual caminho cada cliente usa.

## Risks / Trade-offs

- **Formato exato do stream-json e de `--resume` não verificado neste design.** Como no spike original do opencode (mapeamento SSE → RunEvent), é preciso rodar a CLI real dentro da imagem candidata e observar o JSON linha a linha antes de fechar o parser do shim — tasks.md inclui essa verificação como primeiro passo, antes de qualquer código definitivo do shim ou do `ClaudeCodeHarness`.
- **Caminhos de Landlock para `~/.claude` são um achado, não uma suposição.** Como os `readable_paths`/`writable_paths` do perfil opencode (achados por `strace -f` real), os do claude-code precisam da mesma verificação real dentro do container candidato — tasks.md pede isso explicitamente, sem copiar um palpite de caminhos. **Já verificado (task 1.4):** além de `~/.claude/**` e `~/.claude.json` (config global, write atômico via `.tmp.*`), a CLI também lê/escreve `~/.config/anthropic/{active_config,configs/default.json}` — uma segunda árvore de config fora de `~/.claude` que o design original não previa. A CLI também tenta ler um caminho fixo `/home/claude/.claude/remote/{.oauth_token,.session_ingress_token}` (não relativo a `$HOME`, aparentemente assumindo o usuário fixo `claude` de sandboxes cloud da própria Anthropic) — isso é só leitura, falha com ENOENT de forma inofensiva, e deliberadamente não entra em `readable_paths`.
- **Sem gate de aprovação assíncrono para este harness.** Se um editor esperar ver "aguardando aprovação" no chat para uma operação não-SQL (ex.: acesso a diretório fora do workspace) num sistema `claude-code`, isso não vai aparecer — o Landlock já nega essa tentativa no nível do kernel antes de qualquer protocolo de permissão entrar em jogo, então o resultado observável (operação negada) é o mesmo, só sem o aviso em pt-BR no chat. Aceito como non-goal explícito acima.
- **Chat mostra menos granularidade de "tool_output"** até alguém mapear os tipos de bloco do stream-json (`tool_use`/`tool_result`) para os `RunEvent.kind` existentes (`file_edited`/`command_run`/`tool_output`) com a mesma qualidade que o opencode tem hoje — isso é trabalho de implementação, não um requirement novo (o requirement "Detalhe técnico da execução atrás do modo debug" já é agnóstico de harness).
